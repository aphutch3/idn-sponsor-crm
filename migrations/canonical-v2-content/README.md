# canonical-v2-content

Additive content-domain release for the canonical Neon database. Adds a shared,
platform-agnostic content spine plus the `signals` application schema, and registers
both in the `meta` governance catalogs.

**This release alters no existing table, column, constraint or row.** It only creates
new objects and inserts new metadata rows.

## Why this exists

The News Dashboard, X, YouTube, GitHub and LinkedIn surfaces each modelled "a piece of
published content" differently, in a separate Supabase database, with related entities
stored as text arrays. That made cross-channel questions impossible to ask in SQL and
left identity duplicated per platform. This release gives every channel one shared
grain — `content_item` — while keeping platform-specific detail out of it.

## Design rules

1. **One grain for content.** A `content_item` is one addressable piece of published
   content, whatever the platform. Platform differences never become nullable columns
   on the spine; they live in a one-to-one detail table
   (`content_newsletter_item`) or in the app-private `signals` schema.
2. **Relationships are rows, not arrays.** The eight text arrays the dashboard kept on
   `articles` become `content_entity` rows pointing at canonical `person`, `company`,
   `tag`, `event` and `session`. A trigger proves the target row exists, because a
   polymorphic column cannot express that as a foreign key.
3. **Identity stays canonical.** Authorship resolves to `public.person`, ownership to
   `public.company`. This release never invents either from a display name; unresolved
   links stay null and are documented as such in `meta.column_annotation.null_meaning`.
4. **Observations are append-only.** `content_metric` rejects `UPDATE` and `DELETE`.
   Engagement history is a time series, not a current value that gets overwritten.
5. **Membership is a row, not a flag.** A row in `signals.person_profile` *is* the
   statement "this canonical person is Signals-tracked". No `is_signals` boolean is
   added to `public.person`.
6. **Failures are retained.** `signals.reader_cache` stores failed fetches with their
   error, so a retry is a deliberate decision rather than indistinguishable from work
   never attempted.
7. **The taxonomy is not auto-populated.** `public.tag` is a curated, governed
   vocabulary of 27 tags. The dashboard's ~951 raw free-text tags are **not** promoted
   into it. Signals holds `read` on `tag` and `propose` on `entity_tag`.

## Files

Apply in numeric order. The runner does this atomically.

| File | Contents |
|---|---|
| `60_content_additive.sql` | Enums and the eight `content_*` tables |
| `61_content_indexes.sql` | Access paths, each justified by a named query |
| `62_content_triggers.sql` | `updated_at` maintenance, dedup-key normalization, polymorphic target validation, append-only enforcement |
| `63_signals_private.sql` | `signals` schema, `person_profile`, `reader_cache` |
| `64_content_contract.sql` | **Generated.** Catalog annotations, binding targets, app contract |

`64_content_contract.sql` is generated by `gen_contract.py`, which reads the live
column list and fails if any column lacks a hand-authored meaning. Edit the meanings
in `gen_contract.py` and regenerate; never hand-edit the SQL.

## Running it

`canonical-v1/release.py` asserts the `meta` schema does **not** exist, so it cannot be
reused once v1 is deployed. `release_v2.py` is its sibling and asserts the inverse.

```bash
CANONICAL_MIGRATION_DSN='postgresql://...' python3 release_v2.py \
    --database canonical \
    --git-commit <40-hex> \
    --neon-branch-id <br-...> \
    --expected-public-tables 74 \
    --state draft \
    --dry-run
```

Drop `--dry-run` to commit. Guards, all tested:

- connected database must match `--database`
- `meta` must exist and a deployed `schema_release` must be present
- `public` must hold exactly `--expected-public-tables` tables (74 on current `main`)
- none of the ten new tables may already exist
- the release must not already be recorded
- after applying, every new table must exist **and** every new column must have a
  `meta.column_annotation` row, or the whole transaction rolls back

## Verification performed

Rehearsed and applied on `v2-release-rehearsal-2026-09-20` (`br-summer-river-a53ugbqg`),
a fresh branch off `main`. Dry run applied all five files and rolled back to exactly 74
tables and no `signals` schema. Real run recorded five `meta.migration_execution` rows
(sha256 length 64 each) and one `meta.schema_release` row in `draft`.

Behaviour tested directly against the database: dedup-key normalization; blank-name
rejection; the single-owner constraint; repeated URLs with null `canonical_url`
coexisting as distinct placements; `content_entity` rejecting a non-existent target, an
unapproved target kind and a self-relationship, while accepting a real canonical person;
`content_metric` rejecting update and delete; `reader_cache` requiring a body on success
and an error on failure; `updated_at` advancing across transactions; and
`signals.person_profile` requiring a canonical person.

Catalog visibility confirmed: 10 rows in `meta.table_catalog` with a purpose, 106 in
`meta.column_catalog`, zero unannotated columns.

## Known issues flagged for review, deliberately not changed here

- `public.linkedin_post` (30 rows) and `public.social_mention` (483 rows) are
  platform-specific, carry no comment and no `meta` annotation, and are functionally
  superseded by `content_item`. Retiring them is a destructive change and belongs in a
  separate reviewed release.
- `meta.app_contract` holds rows for `idn-events`, `idn-engager` and `idn-surveys`,
  none of which exist in `meta.app`, whose `code` check requires `^[a-z][a-z0-9_]*$`.
  This release registers `idn_signals` in both, matching the constraint.
- Publisher-to-company resolution is unresolved: only 1 of 49 dashboard publishers
  matches a canonical company, and several "publishers" are individuals. Left null.
